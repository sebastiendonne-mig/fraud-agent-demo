## 1. Architecture réelle

**Appels LLM par analyse** [FAIT]
- **1 appel** si le routage vaut STP, ou si aucun rapport de police n'est saisi. **2 appels** si le routage n'est pas STP et qu'un rapport est fourni (`app.js:451`, `app.js:475-478`).
- Ordre fixe : ① scoring (`runScoring`, `app.js:215`) → ② analyse du PV + recours (`runRecours`, `app.js:252`).
- Modèle : `claude-opus-4-7` en dur, avec `max_tokens: 2000` et `thinking: {type:"adaptive"}` (`app.js:153-155`). Le proxy ajoute l'en-tête `anthropic-beta: interleaved-thinking-2025-05-14` (`proxy.js:85`).

## 2. Clé API

**Cas « clé serveur » (la prod, d'après ce qu'affiche la page)** [FAIT, code]
1. Au chargement, `app.js:102` appelle `/api/check`, qui renvoie `{configured: true/false}` sans jamais exposer la clé (`check.js:5`).
2. Si `true` : le champ de saisie est masqué (`app.js:105-108`) et le navigateur envoie un en-tête `x-api-key` vide (`app.js:408-410`, `app.js:150`).
3. Le proxy constate l'absence de clé client et utilise `process.env.ANTHROPIC_API_KEY` (`proxy.js:45-46`, `proxy.js:68`), avec une limite de débit (voir plus bas).

**Cas « clé visiteur »** (visible seulement si le serveur n'a pas de clé) [FAIT]
- La clé est lue dans le champ au moment de l'envoi. Elle n'est **pas** stockée : pas de localStorage, pas de cookie, rien dans le code.
- Elle **est envoyée au serveur** : en-tête `x-api-key` → fonction Vercel `proxy.js:45` → transmise à Anthropic (`proxy.js:83`).
- Le code ne la journalise pas : aucun `console.*` dans `api/` ni dans `app.js`.
- ⚠️ Le texte « Stockée uniquement en mémoire — **jamais envoyée ailleurs** » (`index.html:703`) est **inexact** : la clé passe par la fonction serverless TKoidra. Ce n'est pas dramatique techniquement, mais c'est une promesse fausse affichée devant des prospects.
- **[INCONNU]** Les journaux de la plateforme Vercel enregistrent-ils les en-têtes de requête ? Je n'ai pas vérifié dans la doc. **[HYPO]** Non par défaut.

**Quelle clé en prod ?**
- **[INCONNU]** Lister les variables du projet Vercel a été refusé (403 : le connecteur n'a pas la permission). Je ne peux donc confirmer ni le nom ni la cible de la variable côté Vercel. **[HYPO]** Il s'agit de `ANTHROPIC_API_KEY`, seul nom lu par le code.
- En local, `demo-web/.env` contient une seule variable, `ANTHROPIC_API_KEY` [FAIT]. Le fichier est ignoré par git (`.gitignore:21`). L'historique git ne contient aucun `.env` et 0 occurrence de motif `sk-ant-api` [FAIT]. Le dernier déploiement fait en ligne de commande (`dpl_7n4V…`, juillet) ne contenait pas de `.env` [FAIT, liste des fichiers Vercel].

**🔴 Constat critique : le proxy est un relais ouvert vers la clé serveur** [FAIT]
- `proxy.js:88` transmet **le corps de la requête tel quel**. N'importe qui peut donc POSTer sur `https://fraud.tkoidra.com/api/anthropic` le modèle, le `max_tokens` et le prompt de son choix, et c'est la clé TKoidra qui paie.
- CORS ouvert à tous (`Access-Control-Allow-Origin: *`, `proxy.js:37`).
- La seule protection est une limite de 5 requêtes par heure et par IP, **stockée en mémoire** (`proxy.js:6-11`). Elle est remise à zéro à chaque démarrage à froid, elle n'est pas partagée entre instances, et il suffit de changer d'IP pour la contourner.
- Cette limite compte des **requêtes**, pas des analyses. Une analyse avec recours consomme 2 requêtes, alors que le message annonce « 5 analyses par heure » (`proxy.js:62`).

## 6. Limites d'exécution

**Configuration actuelle** [FAIT]
- `vercel.json` ne contient qu'une réécriture de route. Aucun `functions`, aucun `maxDuration`, aucune région ou runtime explicite.
- Runtime Node 24.x, défini dans les paramètres du projet Vercel, pas dans le repo.

**Doc officielle Vercel (via context7)** [FAIT, doc]
- Avec **Fluid compute** : durée par défaut et maximale de 300 s en Hobby. En Pro et Enterprise : 300 s par défaut, jusqu'à 800 s.
- Sans Fluid, pour les projets antérieurs au 23/04/2025 : Hobby 10 s par défaut (60 s max), Pro 15 s (300 s max).
- La durée se configure avec `functions.<fichier>.maxDuration` dans `vercel.json`, ou avec `export const maxDuration` dans la route.

**Inconnues et hypothèses**
- [INCONNU] Le plan Vercel de l'équipe (Hobby ou Pro) et l'activation de Fluid compute.
- [HYPO] Fluid est actif, puisque le projet a été créé en 2026.
- Aujourd'hui, chaque fonction ne fait qu'un seul appel à Opus, donc on reste loin des limites. En revanche, une boucle d'agent avec plusieurs appels Opus + thinking dans une seule fonction peut s'en approcher. À prévoir : streaming, et/ou une étape par requête.
- [HYPO] `max_tokens: 2000` inclut les tokens de réflexion : risque de réponse JSON tronquée, donc d'échec de `extractJSON` (`app.js:175-180`).

**Doc officielle AI SDK (via context7)** [FAIT, doc]
- Boucle d'outils : `generateText` ou `streamText` avec `tools` + `stopWhen`. **Par défaut `stopWhen = isStepCount(1)`, donc pas de boucle.**
- Conditions d'arrêt intégrées : `isStepCount(n)`, `hasToolCall('nomOutil')`, `isLoopFinished()`. On peut les combiner dans un tableau, et la boucle s'arrête dès que l'une d'elles est vraie. Exemple : `stopWhen: [isStepCount(10), hasToolCall('decisionFinale')]`.
- ⚠️ Le nom dépend de la version : **v7 = `isStepCount`**, les versions précédentes = `stepCountIs` (renommage documenté dans le guide de migration 7.0). Il faudra figer la version.
- Humain dans la boucle : `needsApproval: true` sur l'outil (versions antérieures), remplacé en v7 par l'option `toolApproval` passée à l'appel. `prepareStep` permet de changer de modèle ou d'outils à chaque étape, utile pour un « triage par un modèle rapide ».

## (a) Les 5 constats les plus importants pour la refonte
1. **Ce n'est pas un agent aujourd'hui** : 1 à 2 prompts enchaînés par des `if` dans le navigateur, et 2 étapes sur 4 sont des `setTimeout`. La refonte est une réécriture, pas une évolution. Et le discours actuel (« pipeline agentique 5 étages », « Azure ML ») surpromet.
2. **Le proxy est un relais ouvert sur la clé serveur** : corps transmis tel quel, CORS `*`, limite de débit en mémoire contournable. À corriger **avant** d'ajouter des boucles d'agent, qui multiplient les appels.
3. **L'orchestration doit passer côté serveur** : aujourd'hui les prompts, les règles et le modèle vivent dans `app.js`, donc chez le visiteur. Une boucle d'outils avec décisions typées et validation humaine suppose une fonction serveur qui possède les prompts, les outils et la condition d'arrêt (`stopWhen`).
4. **Le vrai scoring déterministe existe déjà mais n'est pas branché** (`scoring-model.py`, règles + régression logistique), et ses règles divergent du prompt. C'est le candidat naturel pour un **outil** appelé par Claude, plutôt que de laisser le LLM « simuler » un score.
5. **La documentation et le branding sont désalignés avec la réalité** : CLAUDE.md, README et 13 fichiers décrivent une stack Microsoft qui ne tourne pas. Il faut en plus neutraliser des données qui ressemblent à du réel (MACIF, IP routables), et le message « jamais envoyée ailleurs » est faux.
